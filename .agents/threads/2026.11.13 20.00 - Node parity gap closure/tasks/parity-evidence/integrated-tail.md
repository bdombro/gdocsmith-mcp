- **Does not call `fileImport`, assert temporary-document DELETE, failure cleanup, refused-import no-upload ordering, or link provider-created inlineObject IDs into exported tokens.**
- Task5 inspected these assertion bodies but did not run this test; any earlier green suite is separate provenance.

Implementation `src/api.hpp:1488–1598` already creates converted document and extracts image URIs. It returns `{documentId, contentUris}` on success and **does not delete the temporary document**—caller must own cleanup. After receipt of a created upload document ID, readback/URI-count errors currently throw generic exceptions without a durable typed ID receipt. Source's importer helper at original `engine/import.ts:562–619` explicitly retains an error's `documentId` when available and always attempts cleanup through transaction `.finally()` at 305–308.

## Minimal concrete production integration needed (Source3)

1. Extend existing `ImportServices` with a narrowly typed injectable upload operation returning **owned temporary document ID + ordered contentUris**, plus no-auth external HTTP byte-fetch seam if supporting HTTP sources. Use existing pure image header decoder and bounded reads; do not introduce a second provider emulator or transport layer.
2. In `fileImport`, implement the source-grounded once-per-import image session: resolve local/file/http inputs relative to actual input path, read/validate all sources and aggregate errors first, preserve size/pixel/type limits and loss/downscale notes, then upload **after planning/guards approve**. Wire its placeholder→URI map to the **already existing** `TransactionOptions.imageUploads`; preserve source caching/retry semantics and URI order.
3. Keep the known throwaway provider ID alive through success/failure, including API failure after successful creation. Add an owning typed error/receipt channel at existing `DriveClient::imagesUpload` boundary when necessary; no invented ID or retry after unknown creation.
4. Scope cleanup to that exact known temporary document ID using existing `services.deleteFile`, on transaction success **and** failure. Source's cleanup failure returns warning containing retained provider ID; unknown ID must remain unknown, not guessed/deleted. Do not use newly-created target-document rollback identity in place of temporary-upload identity.
5. App import wiring calls existing `DriveClient::imagesUpload` and no-auth byte-fetch adapter, and forwards existing deleteFile. Current app only wires the latter, so the first hook is genuinely missing.
6. For provider-created inline image identities, use authoritative returned/readback identities and assert token→actual `inlineObjects` key linkage; a second import must not insert again. Keep seeded IDs stable, retain existing image identity on replacement where source does, and require changed identity on recreation/movement where source does. Current `contentSend` consumes the revision receipt but does not itself export an image-ID mapping; this **does not prove an implementation defect**, since authoritative readback can resolve the object. It proves that explicit integrated identity/linkage assertions are still needed rather than inferring them from helper counts or image type equality.

Minimal verification handoff for Source3: one real fileImport fixture with relative+file+HTTP synthetic bytes proves single upload/three URI insertions/exact throwaway delete, invalid inputs prove zero sends, and known-upload-identity postcreate failure plus cleanup-failure controls prove retained identity/warning/no blind retry. Actual app transport injection verifies callback wiring. These are existing OB-036 obligations, not a new framework.
